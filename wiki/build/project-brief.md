# Project Brief: LocalThreads PH

> Generated by `/development build` on 2026-05-23

---

## Elevator Pitch
A discovery and e-commerce platform built exclusively for local Philippine clothing brands. Brands get their own fully customizable storefront and tap into the platform's shared audience — giving even startup labels the visibility they deserve. Think Shopee, but community-first and exclusive to homegrown PH labels.

## Target Users
- **Brand Owners** — local PH clothing brands (startups to established) who want an online storefront with full control
- **Shoppers** — buyers who want to discover, browse, and purchase from local PH clothing brands
- **Admin** — platform operator who approves brands, configures shipping, and manages the platform

---

## MVP Features

### 1. Brand Storefront
Each brand gets a fully editable public page.
- **User flow:** Brand owner logs in → navigates to storefront editor → updates logo, banner, brand story, social links, color theme → saves → changes reflect live on public page
- **Key requirements:** Rich text editor for brand story, image upload for logo/banner, social link fields (Instagram, TikTok, Facebook), public URL at `/brands/[slug]`

### 2. Product Management
Brands self-manage their full product catalog.
- **User flow:** Brand owner → Dashboard → Products → Add Product → upload photos (up to 8), set name/price/description/category/stock → publish → product appears on storefront and discovery feed
- **Key requirements:** Multi-image upload (direct to Cloudinary via signed preset, max 5MB each), product categories, stock tracking, draft/published state, edit and delete

### 3. Discovery Feed & Search
The homepage that drives shared visibility across all brands.
- **User flow:** Shopper lands on homepage → sees featured brands + new products → scrolls feed → clicks brand or product → views storefront or product detail page
- **Key requirements:** Featured brands section, newest products feed, filter by location (Cebu, Manila, etc.), filter by category/style, search by brand name or product keyword

### 4. Checkout & Payment
End-to-end purchase flow with PH-native payment methods.
- **User flow:** Shopper adds product to cart → reviews cart → enters shipping address → selects shipping option (admin-configured) → pays via GCash / Maya / credit card → receives confirmation email + in-app notification with order number and details
- **Key requirements:** Cart persistence, PayMongo integration (GCash, Maya, cards), HMAC-SHA256 webhook signature verification, order number generation, confirmation email via Resend

### 5. Order Management
Shopee-style order tracking for both sides of the transaction.
- **User flow (shopper):** Dashboard → Orders → see list with statuses → click order → view details, tracking number, estimated delivery
- **User flow (brand owner):** Dashboard → Orders → see new order notification → mark as Shipped (enters tracking number) → order moves to To Receive for shopper → shopper marks Received → status moves to Completed
- **Key requirements:** Order state machine (Pending Payment → Paid → To Ship → Shipped → To Receive → Completed → Cancelled), email + polling notifications at each state change, tracking number field, order history for both users

## Supporting Systems

### Brand Approval Flow
- Brand signs up → shop created in **Pending** state (not publicly visible)
- Admin reviews in Admin Dashboard → Approves or Rejects with optional note
- On approval: brand email notification sent, storefront goes live
- On rejection: brand notified with reason

### Admin Dashboard
- Pending brand applications queue (approve / reject)
- Platform-wide shipping configuration (courier selection, rate setup via Shipmates)
- All brands listing with status management

### Brand Owner Dashboard
- Order inbox with status filters (New, To Ship, Shipped, Completed)
- Product management (CRUD)
- Storefront editor
- Basic stats: total orders, revenue, product views

### Shopper Dashboard
- Order history with status filters (To Ship, To Receive, Completed)
- Order detail pages with tracking

- **Brand Owner:** Sign up → build storefront → await admin approval → go live → upload products → receive order notification → mark as shipped → enter tracking number
- **Shopper:** Browse discovery feed → view brand storefront → add to cart → checkout + pay → receive confirmation → track order status → mark as received
- **Admin:** Review pending brand applications → approve/reject → configure Shipmates shipping rates for all shops

## Tech Stack

| Layer | Choice | Why |
|-------|--------|-----|
| Frontend | Next.js 16.2.6 (App Router) + React 19 | SSR — brand/product pages are Google-indexable from day one |
| Backend | NestJS | Structured and opinionated — keeps a solo dev organized across complex domain |
| Database | PostgreSQL | Relational data (users, orders, products, brands) fits perfectly |
| ORM | Prisma | Best DX for solo devs — auto-generated types, easy migrations |
| Auth | Passport-JWT + refresh tokens | Short-lived access tokens (15min) + server-side revocation for role-based multi-tenant security |
| Styling | Tailwind CSS + shadcn/ui | Fastest way to build a polished UI alone |
| API Style | REST | Straightforward, well-understood, easy to debug |
| Payment | PayMongo | PH-native — supports GCash, Maya, credit/debit cards |
| Shipping | Shipmates (abstraction layer) | PH shipping aggregator — J&T, Ninja Van, GoGo Express via one API |
| File Storage | Cloudinary (direct upload) | Browser uploads direct via signed preset; NestJS only generates signed URL |
| Email | Resend | Clean API, great free tier, lives in NestJS only (not Next.js edge) |
| In-app Notifications | Polling (20s interval) | SSE breaks on Railway proxy timeouts; polling is boring and reliable |
| Docker | Yes | Runs PostgreSQL locally |
| Deployment | Railway (backend + DB) + Vercel (frontend) | Both have generous free tiers, zero-config deploys |
| Monorepo | pnpm workspaces | Frontend + backend in one repo with shared types package |

## Architecture Decisions

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| 1 | Auth approach | Passport-JWT + refresh tokens | Custom JWT has no revocation — banned brand owners retain API access until token expiry |
| 2 | Real-time notifications | Polling not SSE | SSE long-lived connections get killed by Railway proxy timeouts |
| 3 | File uploads | Browser → Cloudinary direct | Routing large files through NestJS wastes Railway egress and slows uploads |
| 4 | Multi-tenant isolation | brandId guard on every query | Prisma doesn't enforce this; explicit guard prevents Brand A seeing Brand B's data |
| 5 | Order flow | Explicit state machine | Enum + allowed transitions map; server rejects invalid state jumps with 422 |
| 6 | Shipping | ShippingService abstraction | Shipmates has low API maturity; wrapper lets you swap couriers without rewriting callsites |
| 7 | Build order | Critical path first | Payment → order → notification → shipping chain is the product; everything else is UI |

### Data Flow (Critical Path)
```
Shopper pays → PayMongo webhook → verify signature → create Order (Paid)
→ notify Brand Owner (email + polling) → Brand ships → enters tracking number
→ Order status: Shipped → notify Shopper → Shopper marks Received
→ Order status: Completed
```

## Review Notes
Architecture reviewed by CTO and Technical Lead agents. Key findings acted on:
- Switched from custom JWT to Passport-JWT with refresh tokens and server-side revocation
- Switched from SSE to polling for in-app notifications (Railway proxy timeout issue)
- Added HMAC-SHA256 PayMongo webhook verification as a hard requirement
- Established Cloudinary direct-upload pattern from day one
- Added multi-tenant brandId guard pattern
- Added ShippingService abstraction layer over Shipmates
- Added explicit order state machine with server-side transition validation
- CTO recommendation: build the payment → order → shipping critical path before any UI feature
