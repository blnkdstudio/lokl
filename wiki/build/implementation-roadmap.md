# Implementation Roadmap: LocalThreads PH

> Generated by `/development build` on 2026-05-23

---

## Build Order

Features are ordered by dependency — each phase builds on the previous. The CTO's guidance: **the payment → order → notification → shipping chain is the product**. Build that critical path before any discovery or storefront UI.

---

### Phase 1: Foundation
> Handled automatically by `/development build`. Project scaffolded, dependencies installed, DB running.

- pnpm monorepo with `apps/web` (Next.js) and `apps/api` (NestJS) and `packages/types`
- PostgreSQL running in Docker
- Prisma schema initialized
- Base environment configuration

---

### Phase 2: Auth & User Roles
- **Why first:** Every other feature depends on knowing who the user is and what role they have. No feature can be built without this.
- **Scope:**
  - User registration and login (Shopper + Brand Owner flows)
  - Passport-JWT with short-lived access tokens (15min) + refresh tokens (server-side store, revocable)
  - Role-based guards: `Shopper`, `BrandOwner`, `Admin`
  - Password reset via email (Resend)
  - NextAuth session wiring on frontend (or direct JWT cookie handling)
- **Dependencies:** Phase 1
- **Estimated complexity:** Medium

---

### Phase 3: Brand Onboarding & Approval Flow
- **Why next:** Brand Owners need an account and an approved shop before any product or storefront work makes sense. Admin approval gates all brand content.
- **Scope:**
  - Brand registration form (name, description, logo, location, social links)
  - Brand stored in `Pending` state on creation
  - Admin dashboard page: pending brand queue, approve/reject with optional note
  - On approval: brand status → `Active`, confirmation email sent to owner
  - On rejection: rejection email sent with reason
  - Brand public slug generation (`/brands/[slug]`)
- **Dependencies:** Phase 2
- **Estimated complexity:** Medium

---

### Phase 4: Product Management
- **Why next:** Products are the core inventory of the platform. Required before checkout or discovery can exist.
- **Scope:**
  - Product CRUD for Brand Owners (name, description, price, category, stock, status)
  - Multi-image upload: browser → Cloudinary signed preset → NestJS saves Cloudinary URLs
  - Max 8 images per product, max 5MB each, allowlist: jpeg/png/webp
  - Product draft/published toggle
  - Brand Owner dashboard: product listing, edit, delete
  - Product detail page (public, SSR for SEO)
- **Dependencies:** Phase 3
- **Estimated complexity:** Medium

---

### Phase 5: Critical Path — Checkout & Payment
- **Why next:** This is the core of the business. Build it before discovery so you can test end-to-end with real test credentials.
- **Scope:**
  - Cart (session or DB-persisted)
  - Shipping address form
  - Shipmates integration: `ShippingService` abstraction → fetch rates → display options
  - PayMongo checkout session creation
  - PayMongo webhook handler (HMAC-SHA256 signature verification)
  - Order creation on payment confirmation with order number generation
  - Order state machine: `PendingPayment → Paid → ToShip → Shipped → ToReceive → Completed → Cancelled`
  - Confirmation email to Shopper and Brand Owner (Resend, from NestJS)
  - Polling endpoint: `GET /notifications/unread` (20s interval on frontend)
- **Dependencies:** Phase 4
- **Estimated complexity:** Large
- **Note:** Use ngrok or Cloudflare Tunnel locally to receive PayMongo webhooks during development

---

### Phase 6: Order Management Dashboards
- **Why next:** Now that orders exist, both sides need to manage them. This completes the transaction lifecycle.
- **Scope:**
  - Brand Owner order dashboard: New / To Ship / Shipped / Completed tabs, order detail, mark as Shipped (enter tracking number)
  - Shopper order dashboard: To Ship / To Receive / Completed tabs, order detail with tracking number
  - State transition emails at each step (Resend, from NestJS)
  - Polling-based in-app notification badge (unread count)
- **Dependencies:** Phase 5
- **Estimated complexity:** Medium

---

### Phase 7: Brand Storefront (Public Pages)
- **Why next:** With products, orders, and auth all working, the storefront becomes a clean display layer over existing data.
- **Scope:**
  - Public brand page at `/brands/[slug]` (SSR, Google-indexable)
  - Brand story, logo, banner, social links
  - Brand's published product catalog
  - Storefront editor for Brand Owners (live preview)
  - Custom theme color selection
- **Dependencies:** Phase 4
- **Estimated complexity:** Medium

---

### Phase 8: Discovery Feed & Search
- **Why last among core features:** Discovery is the growth engine, but it requires real brands and products to be meaningful. Build it last so it's populated on launch.
- **Scope:**
  - Homepage: featured brands section + newest products feed
  - Search: by brand name or product keyword (PostgreSQL full-text search)
  - Filters: location (Cebu, Manila, etc.), category, style
  - SEO meta tags on all public pages (brand + product)
- **Dependencies:** Phase 7
- **Estimated complexity:** Medium

## Recommended Workflow

After `/development build` completes, build each feature using:

1. `/development plan` — design the feature (interactive session)
2. `/development implement wiki/features/{feature-name}` — build it with agents
3. `/development ship` — commit and push
4. Repeat for next phase

## Cross-Cutting Concerns (apply to every phase)

- **Multi-tenant isolation:** Every Prisma query that touches brand-owned data must include `WHERE brandId = [jwt.brandId]`. Establish this pattern in Phase 3 and never deviate.
- **Prisma migrations:** Run `prisma migrate deploy` as a Railway pre-deploy step, never on application startup.
- **Prisma connection limit:** `DATABASE_URL` must include `?connection_limit=5&pool_timeout=20`
- **Resend emails:** All email-sending code lives in NestJS only — never in Next.js API routes or Server Actions (edge runtime incompatibility)
- **Cloudinary uploads:** Always browser → Cloudinary direct via signed preset. NestJS generates signed URL and saves the resulting Cloudinary URL only.
- **pnpm + Vercel:** Set root directory to `apps/web` in Vercel project settings and use `vercel.json` with `installCommand: "pnpm install --frozen-lockfile"`

## Notes

- **Start with Phase 5 as the integration test target** — get a real PayMongo test payment flowing into a real order before adding any more UI. This validates the entire backend before the frontend exists.
- **Shared types in `packages/types`** — define `Order`, `Product`, `Brand`, `User` interfaces there from Phase 2 onwards so frontend and backend never drift.
- **Shipmates API** — budget extra time; their documentation is less mature than global equivalents. The `ShippingService` abstraction lets you stub it during early development.
